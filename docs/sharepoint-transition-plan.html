Moving ANCHOR onto SharePoint

ANCHOR today is a Next.js prototype with mock data and no backend. This plan picks a SharePoint architecture, maps every screen to it, and lays out a phased move that fits the 90-day discovery pilot.

Bottom line

Build ANCHOR as a set of SharePoint Framework (SPFx) web parts on a dedicated communication site, with SharePoint lists and a records library as the data store and Power Automate for ingestion, alerts and approvals. SPFx keeps the existing React components, which is most of the work already done, and gives you full control over the precedence, acknowledgement and integrity UX that a Power Apps canvas app would flatten.

Two constraints shape everything else. SharePoint Online in the Navy tenant is an unclassified and CUI environment, so the SECRET and CONFIDENTIAL traffic in the prototype's data model is out of scope. And SharePoint Online has no disconnected mode, so EMCON support becomes a cached read-only export rather than the prototype's sync queue.

Fallback: if the tenant will not deploy custom SPFx packages to the app catalog, build the same data layer and use a Power Apps canvas app embedded on the site. Confirm this in week 1; it is the single biggest unknown.

What this plan assumes

  • Tenant: the Navy's Microsoft 365 DoD tenant (Flank Speed, IL5). If the pilot runs in a different tenant (GCC High or commercial), the architecture holds but approvals and endpoints change.
  • Goal: a working pilot that real watchstanders use, not just a place to host the clickable demo. If you only need a demo link inside SharePoint, skip to option C in the comparison; it is a one-day job.
  • Scope: UNCLASSIFIED and CUI message traffic for COMSUBLANT first, matching the requirements package.
  • Team: you plus one or two developers, with a tenant SharePoint admin who can approve app catalog deployments and site creation.

Where SharePoint pushes back on the requirements

These are the requirements from the ANCHOR package that SharePoint does not meet out of the box. Each needs a design answer before any code moves.

Blocks scope

Classification

SharePoint Online in the DoD tenant is accredited to IL5, which covers CUI but not classified data. SECRET traffic would need a SIPRNet SharePoint farm and a separate build. Drop SECRET and CONFIDENTIAL from the pilot data model.

Changes design

Offline and EMCON

SharePoint Online pages do not work disconnected, and acknowledgements cannot queue locally for later sync. Plan for a pre-EMCON export (a PDF briefing and a CSV of open acknowledgements) and record acknowledgements on reconnection, with the offline time noted.

Needs approval

C2OIX ingestion

SharePoint cannot pull from C2OIX by itself. The likely path is C2OIX delivering to an organizational mailbox, with Power Automate parsing each message into the library. This connection needs its own approval from the C2OIX program office and the tenant's cyber team.

Needs care

Immutability

SharePoint items are editable by default. Use Microsoft Purview retention labels that declare each message a record, which locks content and metadata against edit and delete. Store the SHA-256 computed at ingest and re-check it on display.

Needs care

Volume

Any list query that touches more than 5,000 items is blocked by the list view threshold. Index the columns you filter on (received date, precedence, type, lifecycle) and split the message library by year.

Needs care

Access by command and group

Per-item permissions do not scale; a list slows sharply past a few thousand unique permission scopes. Put each access group in its own library or site and grant access with Entra ID groups.

Open

AI summaries

Which AI service is authorized in the DoD tenant decides this feature. Leave summaries out of the pilot unless an approved service is in place, and keep the "Not authoritative" treatment if they come back.

Recommended architecture

The SPFx web parts replace the in-memory store in src/lib/store.tsx with a thin data service that talks to SharePoint. Everything the user does (read, acknowledge, request a subscription) becomes a list write, and SharePoint's own audit log plus an ANCHOR audit list replace the mock audit trail.

Migration phases

Sized to fit inside the 90-day discovery pilot, with the go or no-go points where a tenant decision could change the path.

WEEKS 1 TO 2

Confirm the tenant

Meet the Flank Speed SharePoint admin and cyber team. Confirm custom SPFx is allowed, which Power Automate connectors are allowed, how C2OIX can reach a mailbox, and what AI service (if any) is authorized. Request the site and a dev site.

Exit: written yes or no on SPFx. A no switches the UI to option B; the rest of the plan stays.

WEEKS 2 TO 4

Data layer and ingest

Create the lists and library by script (PnP provisioning template, kept in the repo). Apply indexes and the record retention label. Build the ingest flow against a test mailbox, loading the prototype's mock messages first, then sample real UNCLAS traffic.

Exit: a message sent to the mailbox shows up as a locked record with a matching hash in under 5 minutes.

WEEKS 3 TO 7

Port the screens

Scaffold an SPFx solution, move types.ts, format.ts, briefing.ts and the components across, and replace store.tsx with a SharePoint data service. Order: Watch Turnover (simplest), Messages and detail, Home and alerts, Subscriptions, Briefings, Reports, Audit. Swap Tailwind for scoped SCSS or keep Tailwind with a prefix, so styles do not leak into SharePoint chrome.

Exit: every screen in the table above works against real lists on the dev site.

WEEKS 6 TO 8

Workflows

Acknowledgement escalation, subscription approval, mandatory subscriptions from group membership, Teams and email alerts by precedence.

Exit: a FLASH test message alerts the right group, and an unacknowledged one escalates on schedule.

WEEKS 8 TO 10

Pilot with one unit

One submarine squadron staff or one boat's in-port team uses ANCHOR alongside their current process. Measure time to find a message, acknowledgement rate and time, and missed-message reports.

Exit: pilot metrics for the COMSUBLANT decision brief.

WEEKS 11 TO 13

Decision and handoff

Brief results, decide whether to scale, and record what scale would need (Dataverse, more commands, a classified version).
